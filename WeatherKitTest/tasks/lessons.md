# Lessons

- Session start: follow the AGENTS workflow by creating `tasks/todo.md` before implementation work and record outcomes here after verification.
- For an app-name-only rebrand in Xcode, prefer changing `PRODUCT_NAME` plus the product file reference instead of renaming the target or scheme. That updates the shipped `.app` name and bundle display name while keeping existing build commands and automation stable.
- For this filesystem-synced Xcode project, new files are auto-added to the target; that speeds up shell refactors, but non-code AGENTS artifacts like `tasks/*.md` also end up in the app bundle unless we explicitly exclude them later.
- When replacing a popover-only shell with a hybrid scene architecture, verify `WindowGroup` launch behavior immediately and suppress automatic launch so the status-bar workflow stays intact.
- Centralizing weather-effect gating in a single policy is safer than per-view ad hoc conditions; it prevented the energy-saver reduced-animation path from silently becoming unreachable again.
- Do not read `NSApp` from singleton stored-property initialization. In SwiftUI app startup, shared objects can be created before AppKit has finished registering the application, so active-state reads must happen after launch or through a safe deferred sync point.
- For sidebar location workflows, keep highlighted suggestion state local to the sidebar view and reconcile persisted selection in the model by stable saved-location IDs; that split keeps keyboard UX lightweight while preventing reorder/delete drift.
- A “Current Location” row needs its own fixed identity. If it reuses the shared active forecast name and weather indiscriminately, the sidebar becomes misleading as soon as a saved city is selected.
- For large overview redesigns, build a new hierarchy container rather than wrapping the old monolithic stack. Recomposition is safer when the new screen owns the order directly and only reuses focused helper views.
- Forecast strips and time labels must format in the forecast location’s time zone, not the Mac’s current time zone, or saved-city views become subtly wrong even when the data is correct.
- Compact menu-bar popovers need pinned primary actions and a scrollable content region; trying to make every section fully fit a fixed-height surface causes clipped controls and unreliable glanceability.
- Do not reuse the main window’s heavy animated weather backdrop inside the popover. Menu-bar surfaces read better with restrained gradients and just enough polish to preserve hierarchy.
- Dedicated destinations should not inherit overview-navigation side effects. If selecting a new location always forces the app back to Overview, every other destination feels temporary and fragile.
- Embedded map interaction rules and full-destination map interaction rules are different. The legacy card should keep wheel scrolling with the parent surface, while the dedicated map destination should reclaim wheel zoom for the map itself.
- For alert workspaces, keep selection state in the destination and reuse the existing detail parser/view stack underneath. That yields a better Mac list-detail flow without rewriting the parsing pipeline.
- App activity is not a reliable proxy for effect visibility. Animation policy should key off whether a weather surface is actually visible, or hidden windows and closed popovers will keep spending work.
- Any self-rescheduling visual effect needs explicit cancellation on disappear. Recursive `DispatchQueue.main.asyncAfter` chains are easy to leak across view lifetime changes.
- Saved-location refresh should be governed by cache staleness and per-location in-flight coordination, not by blunt “refresh everything” passes. That keeps background freshness without competing with the active forecast request.
- If a value model is created from background refresh work, make its initializer explicitly nonisolated/sendable at the model boundary instead of sprinkling actor hops through the caller.
- If the app should only ever have one primary forecast window, use a `Window` scene instead of `WindowGroup`. That keeps menu commands and popover actions from silently opening duplicates.
- Search focus requests cannot live only inside the sidebar view. When the sidebar can be collapsed, the parent shell has to reopen that column and hand the child a consumable focus token.
- For compact saved-location rows, local time is cache data just like temperature and condition. If the cache is missing a time zone, treat that as incomplete data and refresh it instead of pretending the row is finished.
- A popover redesign should treat management UI as secondary chrome. If saved locations or CTA buttons take more vertical space than forecast content, the surface stops being useful at a glance.
- When switching between saved locations on a compact weather surface, clear stale forecast detail immediately and fall back to cached summary data until the fresh hourly and daily payloads arrive.
- Never blank the weather surface before current location is actually resolved. A current-location request can stall or time out, so the app should keep the last usable forecast visible until coordinates arrive.
- For a fixed-size popover, put flexible lower sections inside a constrained scroll region and keep the identity-bearing header inside the hero itself. Otherwise SwiftUI will compress the wrong section when the content budget gets tight.
- For an `LSUIElement` weather app, explicitly enforce accessory lifecycle behavior in the app delegate. Do not rely on default last-window termination behavior when the primary surface is a transient popover.
- Expandable cards should not repeat the same summary text in both the collapsed header and expanded body. If the expanded body contains the narrative, hide or swap the header preview while expanded and dedupe model-provided short/long variants.
- A popover command-specific progress affordance needs command-specific state. Generic surface loading is not enough for actions like "use current location," where users expect the initiating button itself to show active feedback immediately.
- An `NSPopover` that keeps the same `NSHostingController` will also keep SwiftUI scroll position and other transient view state. If the popover should feel fresh on every open, drive its root identity from a per-presentation token.
- For a Mac weather app, do not force every current-location refresh through a fresh Core Location fix. Check recent system and app-known locations first, or the UI will feel hung while desktop location services reacquire a position.
- A dedicated macOS `Settings` scene should not reuse a compact overlay stack verbatim. Keep the preferences window as a split, desktop-sized surface and let any overlay settings entry be a thin wrapper around the same shared settings content.
- If a scene-level wrapper view adds no behavior, prefer instantiating the underlying root view directly in the app scene declaration. It removes one more symbol the compiler/indexer has to resolve and makes entry-point build errors easier to reason about.
- SwiftUI `visualEffect` and `scrollTransition` closures run in sendable contexts. If shared motion tokens live on the main actor by default, cache those values outside the closure or the build will pick up avoidable actor-isolation warnings.
- A location-request timeout must start when an actual location fix begins, not when a permission prompt begins. If the timer starts too early, a slow auth decision can cancel the request before `locationManagerDidChangeAuthorization` ever gets a chance to continue.
- In a request lifecycle that can resolve immediately from cached/system state, do not queue the loading-flag mutation with `DispatchQueue.main.async`. A deferred “start loading” block can run after the request already finished and leave progress UI stuck on forever.
- Current-location lookup and downstream weather loading need separate phases and separate timeouts. Otherwise the UI can imply that Core Location is still failing when coordinates were already resolved and the real stall is in WeatherKit or a follow-on network fetch.
- On macOS, do not model Core Location authorization exactly like iOS. Apple documents that macOS prompts for permission when you start a location service, so a `.notDetermined` flow that waits on `requestWhenInUseAuthorization()` can leave an `LSUIElement` app stuck in a pending state instead of ever starting location resolution.
- A menu bar app should not treat a permission error as the end of the UX. When a system prompt may be hidden or deferred, bring a real window forward for first-time authorization and offer a one-click shortcut into the relevant System Settings pane.
- Verify the privacy usage-description key for the target platform before debugging permission flow. A macOS app using the iOS location plist key can look like a runtime authorization bug when the real problem is missing platform-correct TCC metadata.
- Do not use SwiftUI view lifecycle alone as the truth for macOS window visibility. A scene can stay alive while fully occluded, so heavyweight backdrops and maps need an AppKit visibility signal and an explicit offscreen suspension path.
- If a macOS SwiftUI window suddenly pegs the CPU while idle, sample the live process before blaming animations. A toolbar `Picker` in `.principal` can fall into an AppKit size/constraint loop, especially with custom titlebar styling.
- For sidebar lists that show local times, never build `DateFormatter` inside a row body/computed view property. Cache formatters by time zone or precompute the string in the model, because repeated SwiftUI layout passes can turn formatter creation into a CPU hot path.
- When suspending offscreen work in a split-view window, suspend the sidebar too, not just the detail pane. Hidden list rows can still burn CPU through layout, formatting, and scroll-effect modifiers even if the main content is paused.
- When `NavigationSplitView` is already animating a sidebar width change, avoid layering delayed child-panel hide/reveal choreography and heavy detail-surface compositing on top of it. A simpler state-driven motion path with lighter detail transforms feels faster and smoother.
- In SwiftUI hot paths, never call `CLLocationManager.authorizationStatus` from a view-driven computed property. Cache authorization state in the model and refresh it from delegate or app-lifecycle events, or Core Location can turn simple body evaluation into repeated synchronous XPC/TCC work.
- A successful rebuild does not change an already-running Xcode debug PID. When investigating CPU regressions, always compare against a freshly relaunched debug process or a newly launched standalone build before deciding the latest patch failed.
- Offscreen suspension on macOS has to include the titlebar toolbar, not just the content view tree. SwiftUI/AppKit toolbar items can keep churning through layout and menu-form updates even when the main body has already fallen back to a cheap hidden-window placeholder.
- On macOS, a “washed out” SwiftUI window can come from both the AppKit window and the SwiftUI surfaces. If the `NSWindow` is clear/non-opaque and the weather backdrop also uses semi-transparent daytime colors, even correctly layered cards can look invisible unless the window, backdrop foundation, and shared glass tokens all provide real substrate.
- SwiftUI views do not become reactive just because their formatting helpers read `UserDefaults`. If a unit or preference change should refresh visible values immediately, the destination must observe that preference with `@AppStorage` or another reactive source, and any fallback “refresh” method used by settings needs to publish `objectWillChange` for `ObservedObject` consumers.
- For cross-window SwiftUI deep links into a specific card, publish a one-shot navigation request at the shell level using stable model identity and let the destination view consume it after expanding its own state. Reaching directly into child `@State` or duplicating identifier parsing across views is brittle.
- Parser-backed SwiftUI detail views need explicit identity when their input model can change. If a view owns local parse state plus an embedded `WKWebView`, wrap that stateful subtree in a key derived from the selected model so switching items cannot reuse stale detail content.
